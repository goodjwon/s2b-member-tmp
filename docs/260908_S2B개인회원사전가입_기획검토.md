## 1. 요약

퍼블리싱과 화면 벨리데이션은 기획서 기준으로 완료하였다. 기획서 내부에서 서로 어긋나는 정의가 3건, 화면이 정의되지 않은 흐름이 3건 확인되었다. 이 중 4건은 HTML 구조에 영향이 있으므로 서버 개발 착수 전 확정이 필요하다.

| 구분 | 건수 | HTML 영향 |
|---|---|---|
| 정책 간 충돌 | 3 | 1건 (가입결과조회 목적지) |
| 흐름·화면 누락 | 3 | 3건 |
| 정의 모호 | 6 | 0건 (서버 정책) |
| 기획서 자체 체크포인트 | 4 | 1건 (개인정보 본문) |

## 2. 정책 간 충돌

### C1. 로그인 방식 범위

| 출처 | 정의 |
|---|---|
| 4p 흐름도 | 공동인증서 로그인 방식만 허용 |
| 5p 가입정책 | 필수가입처리는 공동인증서, 개인이용자 계정 로그인시 모두 포함 |

개인이용자 계정 로그인 시 팝업 노출 여부가 결정되지 않았다. 팝업 호출 조건(서버)에만 영향이 있고 화면에는 영향이 없다.

### C2. 가입결과조회 버튼 목적지

| 출처 | 정의 |
|---|---|
| 13p 가입완료 | 클릭시 마이데스크 > 개인회원 가입 조회 페이지로 이동 |
| 5p 가입정책 | 가입현황 조회는 가입현황 안내 팝업에서 처리. 마이데스크 메뉴 없음 |

퍼블리싱은 나의 가입정보 조회 팝업(28p)으로 연결하였다. 마이데스크 메뉴를 신설할 경우 목록 화면이 추가로 필요하다.

### C3. 다중 학교 공동인증서와 수요기관 1:n 불가

| 출처 | 정의 |
|---|---|
| 4p 흐름도 | 하나의 공동인증서로 여러 개의 학교 등록 가능 |
| 5p 가입정책 | 수요기관 내 중복가입 불가 → 1:n의 가입은 불가 |
| 5p 가입정책 | 기관별 1명 필수가입. 미등록시 서비스 이용불가 |

한 담당자가 여러 학교를 관리하는 경우, A학교에 가입하면 B학교의 필수 인원이 될 수 없다. B학교에 다른 이용자가 없으면 필수 인원을 충족할 수 없어 서비스 이용이 차단된다. 수요기관도 공급업체와 같이 소속 1:N을 허용하거나, 필수가입 차단 정책에 예외를 두는 방향 중 결정이 필요하다.

## 3. 흐름·화면 누락

### M1. 최초가입 흐름의 CI 중복 분기

화면지도(2p)는 휴대폰인증 결과(중복없음/중복있음) 분기를 추가가입에만 배치하였다. 그러나 24p 설명은 "기가입 無 일 경우 회원정보입력으로 이동"이라 CI 대조가 휴대폰인증 시점에 항상 수행되는 구조이다. C3 사례처럼 최초가입(0명)에서도 CI 중복이 발생하므로 최초가입에도 동일 분기가 필요하다.

퍼블리싱은 휴대폰인증 화면에 4가지 분기(중복없음, 수요기관 중복, 공급업체 동일업체, 공급업체 타업체)를 주석으로 명시하였다.

### M2. 공급업체 타업체 "예" 이후 화면

26p는 "예" 클릭 시 소속정보 등록이라고만 정의하였다. 다음이 미정이다.

- 소속 추가 완료 안내 화면 유무
- 개인정보수집 동의 재수집 여부
- "아니오" 시 S2B 메인 이동 — 해당 업체가 0명이면 필수가입 정책(5p)과 충돌

퍼블리싱은 "예" 시 알럿 후 메인 이동으로 임시 처리하였다.

### M3. 이메일 중복체크

| 출처 | 정의 |
|---|---|
| 4p 흐름도 | 이메일 중복체크 → 있음 → 알럿(중복불가 안내) |
| 9p·10p 회원정보입력 | 형식 검증과 인증코드 검증만 정의. 중복체크 없음 |

공급업체 1:N 가입은 같은 사람이 같은 이메일로 여러 업체에 소속되는 구조이므로 이메일 중복불가와 양립하지 않는다. 반대로 이메일 유일성이 없으면 28p 이메일 기반 조회 결과에 타인의 정보가 포함될 수 있다. 이메일 유일성 단위(전체/사람 단위 CI 기준)를 정해야 한다. 퍼블리싱은 중복체크를 포함하지 않았다.
